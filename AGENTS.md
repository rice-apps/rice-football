# AGENTS.md

## Project: Rice Football Analytics Platform

This repository is for a RiceApps project supporting Rice University Football's analytics department.

This file exists to give coding agents and developers enough project context to make good implementation decisions without repeatedly asking for background.

---

# 1. Project Mission

Rice Football's analytics department is relatively young and currently lacks durable data infrastructure.

The current understanding is that analysts work with data from sources such as:

- PFF Premium
- CollegeFootballData / public college football data
- Hudl IQ

The current workflow is highly manual.

Data is downloaded or fetched from external sources, moved around as CSVs or other files, analyzed in tools such as R and R Markdown, rendered into reports, and then sent to coaches as one-time attachments.

This creates several problems:

- data is scattered
- analysts repeatedly pull the same data
- files are passed around manually
- reports can become buried in email
- updating a report requires an analyst to rerun it
- coaches cannot regenerate reports themselves
- different vendors may report different values for similar statistics
- there is no durable single source of truth
- work can disappear when student analysts graduate

The long-term goal is to create infrastructure that survives beyond the current generation of student analysts.

The central project principle is:

> Rice Football analytics work should live in durable infrastructure, not individual laptops, emailed CSVs, or one-off PDF attachments.

# 3. Long-Term Product Direction

The final product is not yet fully defined.

The following represents the current high-level direction based on initial planning.

It should be treated as **directional**, not as finalized product requirements.

## Data layer

A centralized database should eventually ingest data from multiple sources and preserve where each piece of data came from.

Expected sources include:

- CollegeFootballData
- PFF
- Hudl IQ

The database should eventually become a single source of truth for analytics work.

Potential long-term concerns include:

- source/vendor provenance
- player identity matching
- team identity matching
- game identity matching
- raw vendor-specific data
- normalized or cleaned data
- stable database views
- analyst access
- data refresh status
- data validation

## Analyst access

Analysts may eventually access centralized data through:

- an R package
- a Python package
- database views
- internal APIs

Possible future functions might include:

```text
get_plays()
get_players()
get_games()
get_pff_grades()
```

These APIs are not finalized.

## Web application

The current idea is a single web application that may eventually serve multiple user types.

Possible coach-facing functionality:

- view available reports
- select report parameters
- generate updated reports
- download reports
- find previously generated reports
- access shared visualizations

Possible analyst-facing functionality:

- upload report scripts
- test report scripts
- publish reports
- version reports
- upload data
- publish one-off visualizations
- monitor source refreshes
- resolve data matching issues
- access analyst tooling information

These are assumptions until Rice Football confirms them.

## Report execution

The eventual system may allow analysts to upload reusable analysis/report scripts.

Possible technologies include:

- R
- Python
- Quarto
- R Markdown

A future worker may run those scripts against current data and produce:

- PDF
- HTML
- other report output

Potential future concerns include:

- cloud execution
- output storage
- versioning
- rollback
- logs
- package dependencies
- job status
- sandboxing
- error handling

Do not build this yet unless explicitly instructed.

## One-off visualizations

The original concept also includes temporary or one-off HTML visualizations.

Example:

> "Top 15 portal running backs according to our metrics"

These may eventually be hosted and shared without becoming permanent report templates.

# 5. Early Development Philosophy

The early sprints should prioritize:

1. reusable foundations
2. technical learning
3. low coupling
4. parallel development
5. small PRs
6. code that can survive changing requirements
7. avoiding premature abstractions
8. avoiding premature schema decisions

Each sprint is approximately a **3-hour work session**.

This is not a traditional multi-week sprint.

Tasks must therefore be scoped appropriately.

A good Sprint 1 task should:

- be independently executable
- produce something visible or testable
- fit within roughly 3 hours
- avoid waiting on another developer
- result in a small PR
- teach the team something useful

# 6. Sprint 1 Concurrency Rule

All developers are working at the same time.

Therefore, Sprint 1 tasks must not form a dependency chain.

Bad:

```text
Dev 3 finishes
   ↓
Dev 4 starts
   ↓
Dev 5 starts
```

Good:

```text
Dev 1 ──────────────┐
Dev 2 ──────────────┤
Dev 3 ──────────────┤
Dev 4 ──────────────┤
Dev 5 ──────────────┤
Dev 6 ──────────────┤
Dev 7 ──────────────┘
                    ↓
             integrate later
```

If your task would normally depend on another developer's task, create the smallest possible local stub.

Examples:

- use temporary mock data
- make a temporary local component
- create a temporary local type
- hardcode one test response

Do not wait for another branch.

Integration happens after independent work is ready.

# 19. Long-Term Data Design Principles

These are principles to remember later.

Do not implement the full design during Sprint 1.

## Preserve source provenance

If PFF and another vendor provide different values for the same concept, do not silently overwrite one.

We should generally know:

```text
value
source
time/version
```

## Internal identity should be separate from vendor identity

Eventually:

```text
PFF player ID
CFBD player ID
Hudl player ID
```

may all refer to one real player.

A future system may contain something conceptually like:

```text
players
-------
id
name
team_id
position
```

and:

```text
player_external_ids
-------------------
player_id
source
external_id
```

Do not assume this exact schema yet.

## Prefer stable interfaces

Analysts should eventually avoid depending directly on volatile raw vendor tables.

Potentially:

```text
raw vendor data
      ↓
clean tables/views
      ↓
R/Python package
      ↓
analysts
```

This allows internal data storage to evolve without breaking every analysis script.

- TypeScript types
- isolated vendor-specific logic
- reusable components
- readable errors

- implementing future infrastructure early

```text

```

If it uses:

```text
app/
```

without `src`, do not move the whole application just to match this document.

## Client/server boundaries

External API secrets must stay server-side.

Do not expose:

- API keys
- vendor credentials
- database credentials

to client-side JavaScript.

## Environment variables

Never commit secrets.

If an environment variable is needed, add only its name to:

```text
.env.example
```


Never commit the actual key.
